Standpipe

Standpipe runs on your own server and keeps your CI going when GitHub Actions stops starting workflows. Your bots and scripts send their triggers to Standpipe instead of GitHub. While GitHub is healthy, Standpipe passes each trigger on to it. During an outage, it will run the workflow on your own machine instead.

Status: pre-alpha. Only Phase 0 runs today: the gateway in observation mode. It authenticates, deduplicates, authorizes, forwards and records every trigger, but it cannot fail over yet. Phase 1's executor, harness and shadow-ledger packages are written and tested but not wired into any binary, and no drill score has been produced. Failover is planned for Phase 2; the roadmap shows the state of each phase.

Purpose & goals

The problem

GitHub Actions has more incidents than any other GitHub service. In the incident of 6 August 2026, which lasted about 10 hours, GitHub throttled webhook delivery, so pushes and pull requests did not start workflows at all. GitHub reported that self-hosted runners were affected too.

A self-hosted runner does not decide what to run. It asks GitHub for jobs, and GitHub hands them out from its own queue. Dynamic runs-on, ARC and third-party runner providers all work the same way, downstream of GitHub's event-to-job pipeline, so when that pipeline stops they sit idle along with your own runners.

Goals

  • Own the trigger URL, so a CI job can start even when GitHub's event pipeline cannot create one.
  • Run GitHub's self-hosted runners on your hardware in normal times, and fall back to a local executor during an outage.
  • Report every degraded result. A skipped check, a cold cache or a failed correlation shows up as a field and a counter, so a result that says success means the work ran.
  • Fit on small hardware: one Go binary and SQLite, with no npm. The optional Phase 2E edge gateway is the only exception, since it deploys with wrangler. It runs on a VPS or a homelab box, and you can expose it through Cloudflare Tunnel.

Permanently out of scope: translating Actions YAML to another CI language, a code-review UI or issue tracker, a general artifact store, GHES installation, and selling a hosted runner service. Managing runners on your own machines is in scope.

How it works

Architecture

GitHub's control plane has to process an event before a CI job exists. The runner's location only matters after that.

Trigger paths and coverage

PathCarried today byIn Standpipe
Programmatic dispatchGitHub REST APIGateway, from Phase 0
Push / PRGitHub webhooksRef poller: produced in Phase 1, routed in Phase 2
Scheduled (schedule)GitHub cronLocal cron calling the gateway (Phase 2)
repository_dispatchGitHub REST APINo trigger surface; reported as a structural coverage gap
Other eventsGitHub webhooksOut of scope (deployment, check_run, merge_group…)

The coverage gap is the set of triggers that appear in run history but never went through the gateway. It will not reach zero, and Standpipe reports it in two classes: migratable (a known caller using workflow_dispatch, so you can move it to the gateway) and structural (manual UI triggers, repository_dispatch, accepted direct calls).

Request flow (Phase 0)

  • The idempotency reservation and the trigger event are written in one transaction, so every dispatch has a record and no event id points at nothing.
  • A repeated key with the same body replays the stored response. The same key with a different body returns 409 idempotency_conflict. If the first request is still in flight, the gateway returns 409 idempotency_in_progress with Retry-After and does not dispatch.
  • Run correlation has three tiers. Tier 1 reads the run id from the dispatch response. Tier 2, for recovery, matches an injected standby_trigger_id through run-name. Tier 3 falls back to a time window. Each result is labelled exact, inferred, ambiguous or none.

Known limits

  • Deploys that use OIDC cannot run elsewhere: an AWS role that trusts GitHub's issuer will not trust your machine. Phases 1 and 2 run tests and builds, and deploys stay manually approved.
  • In normal times jobs run on GitHub's actions/runner. During an outage they run under act, which matched GitHub's run-level result about 96% of the time in measurement. A matching result does not prove the work ran, so the drill also checks step identity and event payloads.
  • About 40% of real runs talk to GitHub while they execute. Those steps fail in a full outage no matter where they run.
  • Standpipe publishes commit statuses, while Actions produces check runs. A required check that never reports under its name stays pending, so a PR can stay blocked after CI passes.
  • The gateway adds a hop. If it goes down, callers use the committed routing.json and the direct-call runbook.
  • A self-hosted runner on a public repo lets a fork PR run arbitrary code on your hardware. Phase 1a will default to private repos and ephemeral runners.

Getting started

Getting a first real caller through the gateway takes about 15 minutes, including creating the GitHub App. The full procedure is in docs/setup.md; this page gives the short version.

Prerequisites

  • Go 1.27+ (to build from source)
  • A GitHub account or organization where you can create a GitHub App
  • A test repository with at least one workflow that has a workflow_dispatch trigger

Install

There are no release binaries yet. Build both binaries from source:

git clone https://github.com/fatihy101/standpipe.git
cd standpipe
CGO_ENABLED=0 go build -o bin/ ./cmd/...
# bin/standpiped  — the gateway daemon
# bin/standpipe   — the operator CLI

The build needs no C toolchain (SQLite is pure Go), so GOOS=linux GOARCH=arm64 cross-compiles for a Raspberry Pi as well.

Set up a first caller

1. Create the GitHub App

Go to Settings › Developer settings › GitHub Apps › New GitHub App. Any name and homepage URL will do. Turn the webhook off, since Standpipe does not use it. Grant these three repository permissions and no others:

PermissionLevelUsed for
ActionsRead and writeDispatching workflows
MetadataRead-onlyListing repos and workflows
ContentsRead-onlyReading workflow files to validate inputs

Note the App ID, generate a private key (.pem), and install the App on your test repository only.

With actions: write, the App can run arbitrary code in that repository's CI. Use a test repository.

The gateway authenticates as an App because a personal access token belongs to one person, breaks everywhere when it is revoked, and with the repo scope reaches every repository. An installation token lives for one hour and can be limited to a set of repos.

2. Write the configuration

mkdir -p /etc/standpipe
cp ~/Downloads/*.private-key.pem /etc/standpipe/github-app.pem
chmod 600 /etc/standpipe/github-app.pem

standpipe.yaml:

github:
  app_id: 123456                                 # your App ID
  private_key_path: /etc/standpipe/github-app.pem

storage:
  sqlite_path: ./standpipe.db

allowed_targets:
  - repo: you/your-test-repo
    workflows: [probe.yml]                      # lists here
    refs: [refs/heads/main]

callers:                                        # a map, keyed by caller name
  release-bot:
    token_id: tok_a1
    token_hash: ""                              # filled in step 3
    role: caller
    allow:
      - repo: you/your-test-repo
        workflow: probe.yml                     # singular here
        ref: refs/heads/main

allowed_targets defines a set of targets, so its workflows and refs are lists. A caller's allow is a list of {repo, workflow, ref} triples with singular fields. Use the workflow's file name (probe.yml), not its name:. The gateway rejects short ref names like main because a short name can mean a branch or a tag.

standpipe config validate --file standpipe.yaml

3. Mint a token, then create the schema

Mint the token first, because migrate refuses a config with an empty token_hash.

standpipe token create --caller release-bot --token-id tok_a1
# paste the printed token_hash line into standpipe.yaml, then:
standpipe migrate --config standpipe.yaml

The token (spd_tok_a1_…) is shown once. Store it as the caller's secret.

4. Onboard the repository

standpipe onboard --repo you/your-test-repo

Without --workflows it discovers workflow_dispatch workflows and asks for confirmation. It also checks that the App is installed, so a missing installation fails here, before the first trigger.

5. Start the gateway

standpiped --config standpipe.yaml --listen :8443 --admin-listen 127.0.0.1:9090

# in another terminal
standpipe status --config standpipe.yaml

6. Send a real trigger

curl -sS -X POST http://localhost:8443/t/you/your-test-repo/probe.yml \
  -H "Authorization: Bearer spd_tok_a1_..." \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{"ref":"refs/heads/main","inputs":{}}'

You should get a 200 whose body has trigger_event_id, and run_id as well when tier 1 correlation worked. Reading event_id instead returns null. Then trace it:

standpipe trace --config standpipe.yaml <trigger_event_id>

The trace should show resolution exact, source dispatch_response (tier 1), status forwarded and integrity content_sha256 OK.

How to use

Your callers (release bots, cron jobs, deploy scripts, SaaS webhooks) call the gateway instead of GitHub's /dispatches endpoint. The CLI shows who triggers what and traces any single trigger.

Migrating a caller

  1. Add the caller under callers with an allow triple per target.
  2. Mint its token with standpipe token create and store the token in the caller's secret store.
  3. Change the caller's URL from api.github.com/repos/{owner}/{repo}/actions/workflows/{wf}/dispatches to {gateway}/t/{owner}/{repo}/{wf}, add an Idempotency-Key header, and send a full ref (refs/heads/… or refs/tags/…).
  4. Run standpipe inventory --human and check that the caller no longer appears in the migratable gap.

The admin listener (--admin-listen, localhost only) serves /healthz and Prometheus /metrics.

Optional: harden a workflow for outage recovery

Tier 1 correlation needs no change to your workflow. Tier 2 recovers the link to the run when the dispatch response is lost, for example after a timeout or a gateway crash mid-call. To enable it, declare the reserved input and use it in run-name:

name: release
run-name: "release • ${{ inputs.standby_trigger_id || github.run_id }}"

on:
  workflow_dispatch:
    inputs:
      standby_trigger_id:
        description: "Standpipe trigger event ID (auto-injected)"
        required: false
        type: string

The gateway injects the input only when the workflow declares it. It never edits workflow files or requests contents: write, so you add the input yourself.

Exposing the gateway with Cloudflare Tunnel

If Standpipe runs on a homelab box with no public IP, a Cloudflare Tunnel gives callers outside your network an HTTPS URL, and you do not have to open any ports. Expose only the /t/ trigger paths. Use a named tunnel with an ingress rule that matches the path:

cloudflared tunnel create standpipe
cloudflared tunnel route dns standpipe ci.example.com

~/.cloudflared/config.yml:

tunnel: standpipe
credentials-file: /root/.cloudflared/<tunnel-id>.json
ingress:
  - hostname: ci.example.com
    path: ^/t/
    service: http://localhost:8443
  - service: http_status:404
cloudflared tunnel run standpipe

Do not use cloudflared tunnel --url http://localhost:8443, including for quick tests. It forwards every path on the trigger listener, not only /t/.

Never point the tunnel at --admin-listen, which serves /metrics and /inventory. Keep the admin listener on 127.0.0.1, or put it behind Cloudflare Access if you need it remotely. The same will apply to the Phase 1a setup page.

Today only external callers need the tunnel. From Phase 1a, GitHub's workflow_job webhook, sent by the separate runner App, will also reach the gateway through the tunnel on a second, signature-checked path, which will need its own ingress rule; the path name is chosen in the Phase 1a design. The runner agent and the ref poller are planned to make outbound connections only. Neither exists yet, and that design is not yet verified.

Troubleshooting

SymptomCause
503 app_not_foundapp_id names no App. Installing will not fix it; correct the ID.
503 installation_not_foundThe App is not installed on the repo, the repo does not exist, or the App cannot see it. standpipe onboard --repo O/R tells the three apart.
503 credential_expiredThe .pem path is wrong or unreadable.
403 forbiddenRepo or workflow differs between allowed_targets, the caller's allow and the URL. All three must match.
unknown field(s): …allow[0].workflowsPlural field inside a caller's allow; use workflow / ref.
409 idempotency_in_progressThe same key is still in flight. Wait for Retry-After; nothing was dispatched twice.

If the gateway itself is down, follow the direct-call runbook, which has callers use GitHub's API directly until the gateway is back.
